#+author: scs / Codex
#+date: 2026-07-03
#+startup: overview

* Purpose

This report surveys Common Lisp libraries for building text user
interfaces (TUIs), plus the lower-level terminal libraries that a TUI
library is likely to depend on.

The immediate correction: the commonly mentioned library is
=Croatoan=, not =Crocotoan=.  Croatoan is real and useful, but it is not
the whole ecosystem.

This report is intentionally broader than Quicklisp alone.  It includes
Quicklisp/Quickdocs systems, CLiki entries, active and inactive GitHub
and Codeberg repositories, and a few app-local projects that are useful
to mine for ideas even when they are not reusable libraries.

* Method

I treated a candidate as relevant if it met at least one of these
criteria:

- It provides a full-screen terminal UI framework or widget system.
- It provides bindings to a terminal UI backend such as ncurses,
  termbox, notcurses, STFL, S-Lang, or libtcod.
- It provides terminal control primitives that could reasonably support
  a custom TUI layer.
- It appears in Quicklisp, CLiki, GitHub, or Codeberg under Common Lisp
  terminal/TUI/curses searches.

I did not count end-user applications as libraries, but I list notable
applications later because their code may be useful as examples.

The main source buckets checked were:

- Quicklisp current dist metadata, version =2026-01-01=:
  https://beta.quicklisp.org/dist/quicklisp.txt
- Quickdocs pages for individual Quicklisp systems:
  https://quickdocs.org/
- CLiki pages and searches:
  https://www.cliki.net/
- GitHub repository searches for Common Lisp TUI, curses, termbox,
  notcurses, terminal control, and ANSI terminal libraries.
- Codeberg repository searches, especially for Croatoan and related
  projects.

* Evaluation Data Shape

For each candidate, the useful facts are:

- =Name=: system or repository name.
- =Layer=: high-level framework, widget binding, backend binding,
  terminal-control primitive, or presentation helper.
- =Packaging=: Quicklisp, GitHub-only, Codeberg-only, CLiki-only, or
  app-local.
- =Native dependencies=: ncurses, termbox, notcurses, STFL, S-Lang,
  libtcod, SDL/OpenGL, terminfo, or none obvious.
- =Portability risk=: likely issues for LispWorks and SmartOS native
  zones.
- =When to try it=: what kind of project it best fits.

This shape matters because a TUI choice is not just an API preference.
It commits the project to a terminal model, input model, deployment
dependencies, and implementation support story.

* Short Recommendation

For a new Common Lisp TUI project today, I would investigate in this
order:

1. =cl-tuition=, if its model fits and its LispWorks/SmartOS story can
   be verified.
2. =uncursed=, if a curses-like API is wanted without directly adopting
   ncurses.
3. =croatoan=, if ncurses is acceptable and a higher-level widget layer
   is desired.
4. =cl-charms= or =cl-termbox2=, if the project wants to build its own
   framework on a lower-level backend.
5. =charmed= or =ACUTE-TERMINAL-CONTROL=, if avoiding native terminal UI
   libraries is more important than getting a complete widget stack.
6. =tvision=, if SBCL-only is acceptable and a Turbo Vision style
   framework is attractive.

For SCS-style deployment, the first hard gate should be native
dependency viability on SmartOS and LispWorks support.  Anything based
on ncurses, termbox, notcurses, STFL, S-Lang, libtcod, SDL, or OpenGL
needs platform verification before adoption.

* High-Level TUI / Widget Libraries

** cl-tuition / tuition

- Source: https://github.com/atgreen/cl-tuition
- Quickdocs: https://quickdocs.org/cl-tuition
- Layer: high-level TUI framework.
- Quicklisp: yes, as =cl-tuition=, system =tuition=.
- Recent status: active in 2026 based on repository metadata and
  Quicklisp inclusion.

=cl-tuition= describes itself as a Common Lisp library for building
TUIs.  It appears to be one of the newest serious candidates in the
space.

Quicklisp dependency metadata observed:

- =alexandria=
- =asdf=
- =bordeaux-threads=
- =serapeum=
- =trivial-channels=
- =version-string=

The dependency list is encouraging because it does not immediately show
ncurses, CFFI, or another large native terminal backend.  That does not
prove it is native-dependency-free; raw terminal mode and input handling
still need review in the source.

Use when:

- A high-level framework is desired.
- A newer project is acceptable.
- The codebase can tolerate a review pass before depending on it.

Verify before adoption:

- LispWorks support.
- SmartOS terminal/raw-mode behavior.
- Whether it shells out to =stty= or depends on implementation-specific
  stream/file-descriptor behavior.
- Documentation quality and example completeness.

** uncursed

- Source: https://github.com/Plisp/uncursed
- Quickdocs: https://quickdocs.org/uncursed
- Layer: curses-like terminal UI library.
- Quicklisp: yes.
- Recent status: active in 2026 based on repository metadata and
  Quicklisp inclusion.

=uncursed= is a modern terminal library that appears to avoid direct
ncurses dependency while still providing a curses-like abstraction.

Quicklisp dependency metadata observed:

- =alexandria=
- =asdf=
- =cffi=
- =cffi-grovel=
- =cl-setlocale=
- =terminfo=

This means it is not pure Lisp.  The =cffi= and =cffi-grovel= pieces
need to be checked on LispWorks and SmartOS, and =terminfo= behavior
must be verified on the target hosts.

Use when:

- You want a terminal UI library that is lower-level than a complete
  application framework, but higher-level than raw ANSI escapes.
- You want to avoid binding directly to ncurses.
- You are willing to validate FFI and terminfo behavior.

Verify before adoption:

- LispWorks CFFI support in this library.
- SmartOS terminfo database availability and naming.
- Wide-character and Unicode behavior in the terminals SCS actually
  uses.

** Croatoan

- Source: https://codeberg.org/McParen/croatoan
- Quickdocs: https://quickdocs.org/croatoan
- Layer: ncurses binding plus higher-level TUI widgets.
- Quicklisp: yes.
- Related systems: =croatoan=, =croatoan-ncurses=, =ansi-escape=.

Croatoan is the best-known Common Lisp TUI library at the moment.  It
wraps ncurses and also provides higher-level abstractions, so it is not
just a raw binding.

Quicklisp dependency metadata observed:

- =bordeaux-threads=
- =croatoan-ncurses=
- =trivial-gray-streams=
- =cffi= through =croatoan-ncurses=

Use when:

- ncurses is acceptable.
- A practical existing Common Lisp TUI layer is desired.
- You want examples and an ecosystem that other Common Lisp TUI apps
  already use.

Verify before adoption:

- LispWorks support.
- Correct ncurses library names on SmartOS.
- Whether wide-character ncurses is required.
- Input handling for function keys, resize events, mouse, and Unicode.

** cl-tui

- Source: https://github.com/naryl/cl-tui
- Quickdocs: https://quickdocs.org/cl-tui
- Layer: high-level text user interface library.
- Quicklisp: yes.
- Backend: =cl-charms=.

=cl-tui= is an older high-level TUI library built over =cl-charms=.
There is also an older mirror/repository lineage under =lisp-mirror=.

Quicklisp dependency metadata observed:

- =alexandria=
- =anaphora=
- =asdf=
- =cl-charms=
- =cl-containers=
- =osicat=
- =split-sequence=
- =trivial-types=

Use when:

- You specifically want a =cl-charms=-based high-level library.
- The API fits better than Croatoan or =cl-tuition=.

Verify before adoption:

- Maintenance status.
- LispWorks support.
- =osicat= and =cl-charms= behavior on SmartOS.
- Whether its abstractions are mature enough for the planned app.

** tvision / revision

- Source: https://github.com/lispnik/tvision
- Layer: text-mode UI toolkit.
- Quicklisp: not observed in the current Quicklisp dist.
- Primary implementation: SBCL, according to its README.

=tvision= is a very new Common Lisp text-mode UI framework inspired by
Borland Turbo Vision.  Its README presents =revision= as a
CLOS-native text-mode UI framework with overlapping windows, dialogs,
controls, mouse-aware events, palettes, ANSI escape output, and color
fallbacks.

Important constraints from the README:

- SBCL is the stated implementation target.
- It expects a POSIX terminal and =stty=.
- It says no external Lisp libraries are required for build/run/test.

Use when:

- SBCL-only is acceptable.
- A Turbo Vision style UI is desired.
- The project can tolerate a very young dependency.

Do not choose it yet for:

- LispWorks-first code.
- SmartOS deployment without checking =stty= behavior and terminal
  assumptions.

- Quicklisp: not observed in the current Quicklisp dist.

Repository metadata describes this as "The Coalton Omnipotent TUI".
Treat it as an experimental project to inspect, not as a default

Use when:

- Coalton integration is specifically attractive.
- The project can afford source review and possible adaptation.

Verify before adoption:

- Whether it is a reusable library or mainly an experiment.
- Dependency stack.
- LispWorks relevance, which may be low if Coalton/SBCL assumptions are

** tui-lisp

- Source: https://github.com/kulkarniniraj/tui-lisp

- Quicklisp: not observed in the current Quicklisp dist.

Repository metadata describes it as a "Common Lisp based TUI

- You are mining ideas.

** cffi-stfl

- CLiki: https://www.cliki.net/cffi-stfl
- Source: https://github.com/Ramarren/cffi-stfl
- Layer: bindings to STFL, a curses-based widget/forms library.
- Quicklisp: not observed in the current Quicklisp dist.

STFL is a structured terminal forms language/library layered over
curses.  =cffi-stfl= gives Common Lisp access to that world.

Use when:

- STFL's model is specifically desired.
- An older, lower-activity dependency is acceptable.

Verify before adoption:

- STFL availability on SmartOS.
- CFFI build behavior.
- Whether STFL itself is still a good dependency choice.

** cl-tcod

- Source: https://github.com/podiki/cl-tcod
- CLiki: https://www.cliki.net/cl-tcod
- Quickdocs: https://quickdocs.org/cl-tcod
- Layer: libtcod bindings for roguelike/console-style interfaces.
- Quicklisp: yes.

=cl-tcod= is not a normal terminal TUI library.  It targets libtcod,
which is useful for roguelike-style console UIs.  CLiki notes that it
can feel like a modern replacement for some ncurses use cases, but it
uses SDL/OpenGL and therefore is not a pure terminal dependency.

Quicklisp dependency metadata observed:

- =cffi=
- =cffi-libffi=
- =defstar=

Use when:

- The UI is game-like or roguelike-like.
- A windowed console rendering model is acceptable.

Do not choose it when:

- The app must run inside an SSH terminal with no graphics stack.
- SmartOS server deployment is the target and SDL/OpenGL is unwanted.

** sb-screen

- CLiki: https://www.cliki.net/sb-screen
- Layer: S-Lang based console display wrapper.
- Quicklisp: not observed in the current Quicklisp dist.

=sb-screen= is an older wrapper around the S-Lang library.  It belongs
in the same historical family as curses-like console display libraries.

Use when:

- You are researching prior art.

Avoid as a first choice unless:

- S-Lang is already a required dependency.
- The code is reviewed and found suitable for the target implementation.

* Portability and SmartOS Notes

SCS deployment should treat SmartOS native zones as the default hosting
target unless the project says otherwise.  That changes the dependency
calculus.

** Lowest native dependency risk

Likely lower-risk candidates, subject to source verification:

- =charmed=
- =ACUTE-TERMINAL-CONTROL=
- =cl-term=
- =cl-ansi-term=
- =cl-ansi-text=
- =trivial-escapes=

These are mostly ANSI escape/output libraries.  The tradeoff is that
they do less for you.

** Medium risk

Candidates that may be reasonable but need implementation and terminal
behavior checks:

- =cl-tuition=
- =tvision=
- =trivial-raw-io=
- =terminfo=
- =uncursed=

=cl-tuition= looks promising, but its raw terminal strategy must be
reviewed.  =tvision= avoids external Lisp libraries but is SBCL-focused
and uses POSIX terminal assumptions.  =uncursed= avoids direct ncurses
but still uses CFFI and terminfo.

** Higher native dependency risk

Candidates requiring careful SmartOS packaging verification:

- =croatoan=
- =cl-charms=
- =cl-ncurses=
- =cl-fu= / =cl-curses=
- =cl-termbox=
- =cl-termbox2=
- =cl-notcurses=
- =cffi-stfl=
- =sb-screen=
- =cl-tcod=

These depend on native C libraries or graphics stacks.  They may still
be perfectly viable, but they should not be adopted before checking:

- pkgsrc or source-build availability on SmartOS.
- Library names and search paths.
- Wide-character support.
- CFFI or UFFI support under LispWorks.
- Whether the library assumes GNU/Linux-only behavior.

* LispWorks Notes

The Common Lisp implementation target matters.

Likely friction points:

- SBCL-specific libraries: =tvision= is explicitly SBCL-focused.
- UFFI-based code: =cl-ncurses= is old and UFFI-based.
- CFFI-heavy code: =croatoan=, =cl-charms=, =uncursed=,
  =cl-termbox=, =cl-notcurses=, =cl-tcod=, and =cffi-stfl= need
  LispWorks CFFI verification.
- Raw file descriptor code: any library that toggles raw mode directly
  may assume SBCL or Unix stream internals.

Before adopting any candidate for SCS LispWorks-first code, make a tiny
smoke test:

1. Load the system in LispWorks.
2. Enter raw mode.
3. Draw a bordered window.
4. Read a normal key, an arrow key, and a resize event if supported.
5. Restore the terminal after an error.
6. Run the same test through SSH on the intended SmartOS host.

* Practical Trial Plan

The fastest way to choose is to build the same tiny application in a few
libraries.

The test application should contain:

- A bordered main view.
- A status line.
- A scrollable list.
- A small editable text field.
- Keyboard navigation.
- A clean error/exit path that restores the terminal.

Try these first:

1. =cl-tuition=
2. =uncursed=
3. =croatoan=
4. =cl-charms= or =cl-termbox2= as a lower-level baseline
5. =charmed= as the no-native-library baseline

Record for each:

- Load result in LispWorks.
- Load result in SBCL.
- Native dependencies needed.
- SmartOS build steps.
- Lines of application code for the trial.
- How clear the API is to a new maintainer.
- How well errors restore the terminal.

* Candidate Classification Summary

** Best first investigations

- =cl-tuition=: promising new high-level option.
- =uncursed=: promising modern curses-like option.
- =croatoan=: proven and known, but ncurses-based.

** Best lower-level building blocks

- =cl-charms=: curses backend.
- =cl-termbox2=: small backend if termbox2 builds cleanly.
- =charmed=: pure-Lisp ANSI terminal control.
- =ACUTE-TERMINAL-CONTROL=: direct terminal-control prior art.

** Historical or maintenance-only

- =cl-ncurses=
- =sb-screen=
- older =cl-termbox= variants
- =cffi-stfl=

** Not pure terminal TUIs

- =cl-tcod=: useful, but SDL/OpenGL/libtcod-based.
- =clog-terminal=: web/CLOG terminal-like widget.

** Examples, not libraries

- =tinmop=
- =girc=
- =shuffletron=
- =CLabber=
- =gilt=
- =dithcord-tui=
- =cl-netstat=
- =juicebox=
