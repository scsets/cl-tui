* Abstract

This paper tests Common Lisp terminal user interface libraries on the
actual target environment:

- host: =fido.scs.re=
- OS: =SunOS fido.scs.re 5.11 joyent_20260522T154557Z i86pc=
- Lisp: =LispWorks 7.1.0=, using
  =/opt/custom/lispworks/bin/lispworks-7-1-0-amd64-solaris -tty=
- test root: =/opt/tmp/cl-tui-test=
- tools: =/opt/tools/bin= and =/opt/tools/sbin= first in =PATH=

The short answer is:

1. For a real Common Lisp TUI on this machine, rely first on =Croatoan=,
   but do not rely on it unpatched.  It needs a SmartOS/pkgsrc ncurses
   compatibility fix because the installed library is
   =/opt/tools/lib/libncurses.so=, while Croatoan looks for
   =libncursesw.so=.
2. Use =cl-charms= as the lower-level ncurses fallback.  It also works
   once the compiler can see =/opt/tools/include/ncurses=.
3. =cl-tui= (naryl, on =cl-charms=), loads and draws in a PTY after the
   same ncurses fix, but it is older and less attractive as the primary
   choice than Croatoan.
4. =cl-fu= and =raw-binding-ncurses= are viable low-level raw ncurses
   binding candidates.  They are not high-level TUI frameworks, but both
   loaded and drew text in the SSH PTY.
5. Do not currently rely on =cl-tuition=, =uncursed=, =tvision/revision=,
   =cot=, =tui-lisp=, =charmed=, =charming-clim=, =cl-termbox=,
   =cl-termbox2=, =cl-notcurses=, =cffi-stfl=, =cl-tcod/tcod=, or
   =cl-ncurses= for LispWorks 7.1 on this SmartOS host without patching
   or installing additional native libraries.

This is not a paper survey only.  The conclusions are based on ASDF load
tests, native-library checks, and SSH PTY smoke tests on =fido=.

* Research Question

The practical question was not "which Common Lisp TUI library looks good
on GitHub?"  It was:

#+begin_quote
Which Common Lisp TUI libraries can we rely on under LispWorks 7.1 in a
SmartOS native zone, using the toolchain already available under
=/opt/tools=?
#+end_quote

That framing matters.  Many Common Lisp terminal libraries are portable
in the casual sense, but a deployable SCS choice needs all of these to
work together:

- LispWorks compiler and reader behavior.
- ASDF and Quicklisp source loading.
- CFFI or UFFI on LispWorks.
- SmartOS native shared-library names and runtime search paths.
- SmartOS header locations for CFFI grovel.
- SSH pseudo-terminal behavior.
- Terminal database behavior through =TERM= and terminfo.

* Method

** Source Acquisition

Quicklisp was installed under:

#+begin_example
/opt/tmp/cl-tui-test/quicklisp
#+end_example

Direct Quicklisp archive extraction inside LispWorks hit a
=DEFLATE-DECOMPRESSION-ERROR=.  To avoid mistaking that Quicklisp client
problem for library failure, I used Quicklisp dist metadata to compute
source closures, downloaded archives with =/opt/tools/bin/curl=, checked
them with =gzip -t=, and extracted them with =gtar= into:

#+begin_example
/opt/tmp/cl-tui-test/source
#+end_example

The original Quicklisp TUI closure contained 135 ASDF systems from 103
Quicklisp projects.  An additional dependency closure for Git-only
systems pulled 73 ASDF systems from 61 Quicklisp projects, chiefly for
=coalton=, =log4cl=, =dexador=, =shasht=, and their dependencies.

Git-only candidates were cloned under:

#+begin_example
/opt/tmp/cl-tui-test/git
#+end_example

** Test Layers

The work used four layers of testing:

1. Baseline ASDF load using only the normal =/opt/tools= runtime path.
2. Compatibility ASDF load with SmartOS ncurses fixes.
3. Functional SSH PTY smoke tests for high-level viable libraries.
4. Functional SSH PTY smoke tests for low-level ncurses bindings.

The functional smoke tests did not test every key, mouse event, color
pair, resize event, Unicode path, or error path.  They tested the
critical first deployment question: can the library initialize the
terminal, draw, refresh, and restore control under LispWorks through SSH
on SmartOS?

** Compatibility Environment

The ncurses-family compatibility environment was:

#+begin_src sh
PATH=/opt/tools/bin:/opt/tools/sbin:/usr/ccs/bin:/usr/bin:/bin:/usr/sbin:/sbin
CPATH=/opt/tools/include/ncurses:/opt/tools/include
LIBRARY_PATH=/opt/tools/lib
LD_LIBRARY_PATH=/opt/tmp/cl-tui-test/lib:/opt/tools/lib:/usr/lib/amd64:/usr/lib
PKG_CONFIG_PATH=/opt/tools/lib/pkgconfig
TERM=xterm
#+end_src

For the test, I created:

#+begin_example
/opt/tmp/cl-tui-test/lib/libncursesw.so -> /opt/tools/lib/libncurses.so
#+end_example

This symlink was a diagnostic compatibility shim, not my recommended
long-term deployment mechanism.  A production fix should either install
or build a true =libncursesw.so= name, or patch the CFFI foreign-library
definitions to accept SmartOS/pkgsrc =libncurses.so= when
=NCURSES_WIDECHAR= is present.

* Definite Recommendation

** Primary Choice: Croatoan

Use =Croatoan= first for a real Common Lisp TUI on this host.

Reasons:

- It is a real high-level terminal UI library, not just colorized output
  or a raw binding.
- It loaded successfully in LispWorks 7.1 after the SmartOS ncurses
  library-name fix.
- It initialized, drew, refreshed, and exited in an SSH PTY on =fido=.
- It is better suited than raw ncurses bindings for ordinary application
  work because it supplies higher-level structure over ncurses.

The catch:

- Croatoan does not work out of the box on this host because it looks
  for =libncursesw.so= and the installed pkgsrc ncurses package exposes
  =libncurses.so=.

What to fix before relying on it:

1. Replace the test symlink with a deliberate deployment solution.
2. Add a tiny permanent smoke test to the project using Croatoan:
   initialize screen, draw a status line, read one key, and unwind
   through terminal cleanup.
3. Test resize, function keys, arrows, mouse if needed, color pairs,
   and the terminals SCS actually uses.
4. Vendor or pin the exact Croatoan source and ncurses behavior rather
   than relying on live Quicklisp extraction.

** Secondary Choice: cl-charms

Use =cl-charms= if the project wants a lower-level ncurses API or wants
to build its own widget layer.

Reasons:

- It loaded in LispWorks with the =CPATH= and ncurses runtime fixes.
- It drew and refreshed in the SSH PTY.
- It is the backend for =cl-tui=.

The catch:

- Out of the box, CFFI grovel failed because =cc= could not find
  =ncurses.h=.  Adding =/opt/tools/include/ncurses= to =CPATH= fixed
  that.

** Conditional Choice: cl-tui (naryl)

=cl-tui= is technically viable after the same =cl-charms= fix:

- ASDF load: OK under compatibility environment.
- PTY smoke: OK.

I would not pick it as the first choice for a new project unless its API
is exactly what the application wants.  It is older, depends on
=cl-charms=, and gives less confidence than Croatoan as the primary
framework.

** Low-Level Raw Binding Choices

=cl-fu= and =raw-binding-ncurses= both passed load and PTY smoke tests.
They are real candidates if the project wants to own the higher-level
TUI layer.

I would choose one of these only when:

- Croatoan is too opinionated.
- cl-charms is too small or incomplete for the needed ncurses surface.
- We are prepared to write and maintain application-level widgets,
  focus, event dispatch, screen invalidation, and cleanup.

Between the two, =raw-binding-ncurses= appears broader and mechanically
generated, while =cl-fu= is simpler to understand.  Both need deeper API
and maintenance review before production use.

* Failure Analysis

** The ncurses Library Name Problem

The largest false negative in the baseline test was ncurses naming.
Croatoan expected =libncursesw.so=.  SmartOS/pkgsrc installed ncurses
6.6 as =libncurses.so=, while =pkg-config= exposed
=-DNCURSES_WIDECHAR=.

This means the installed library is wide-character capable, but not
named the way many Linux-oriented Common Lisp CFFI definitions expect.

Affected libraries:

- =croatoan=
- =croatoan-ncurses=
- =cl-fu= in some feature configurations
- =raw-binding-ncurses= when it prefers =libncursesw.so=
- any future ncurses binding that assumes Linux-style =ncursesw= names

The compatibility symlink proved viability, but the proper fix should
be explicit.  A project should carry a SmartOS CFFI foreign-library
definition or install a deliberate =libncursesw.so= compatibility link
in a controlled prefix.

** The ncurses Header Problem

=cl-charms= failed at CFFI grovel until the compiler saw:

#+begin_example
/opt/tools/include/ncurses/ncurses.h
#+end_example

Setting this fixed the load:

#+begin_src sh
CPATH=/opt/tools/include/ncurses:/opt/tools/include
#+end_src

The production lesson is the same as for library names: do not rely on
ambient shell luck.  Put the include path in the build environment or
patch the grovel configuration.

** Serapeum FASL Externalization on LispWorks 7.1

Several promising libraries failed through current Quicklisp =serapeum=:

- =tuition= / =cl-tuition=
- =cl-ansi-term=
- =tui-lisp=

The recurring error was in =serapeum level2/units=:

#+begin_example
Object #<pointer out of memory bounds: ...> is of type SYSTEM::MARKER
which is not externalizable to ... t_units ... .64sfasl
#+end_example

That is not a TUI problem per se.  It is a LispWorks 7.1 plus current
Serapeum compile-file problem.  But it is still decisive for adoption:
libraries whose dependency closure includes this Serapeum path are not
reliable here until Serapeum is patched, pinned to a compatible version,
or avoided.

** defpackage :local-nicknames on LispWorks 7.1

LispWorks 7.1 rejected:

#+begin_example
Unknown options in defpackage: ((:LOCAL-NICKNAMES ...))
#+end_example

Affected libraries:

- =uncursed=
- =eu.turtleware.charming-clim=

This may be patchable by removing local nicknames or using a
compatibility layer, but it is not a no-work adoption.

** SBCL-Specific Code

Some projects are explicitly or effectively SBCL-oriented:

- =tvision/revision= uses =SB-EXT= and its README states SBCL as the
  target.
- =ansi-escape= fails in =stty= code because LispWorks cannot find
  =SB-POSIX= and =SB-SYS=.
- =trivial-raw-io= failed on implementation-specific reader syntax.
- =ncurses-leningkoei= says it is for SBCL and uses SBCL/roswell style
  build assumptions rather than ASDF portability.

These are not LispWorks choices without porting.

** Missing Native Libraries

These libraries failed for simple native-library reasons:

| Library | Missing native library |
|---------+------------------------|
| =cl-termbox= | =libtermbox.so= |
| =cl-termbox2= | =libtermbox2.so= would be needed; compile also failed first. |
| =cl-notcurses= | =libnotcurses.so= or =libnotcurses.so.3= |
| =cffi-stfl= | =libstfl.so= |
| =tcod= / =cl-tcod= | =libtcod.so= |
| =parse-rgb= | Pulls =LIBTCOD=, so also =libtcod.so=. |

The package search on =fido= did not find termbox, tcod, or notcurses
in the configured pkgsrc repository.  These could still be built from
source, but doing so would become a native packaging project, not a
Common Lisp library adoption.

** Quicklisp Client Issue

Quicklisp itself installed, but Quicklisp archive extraction inside
LispWorks hit deflate errors.  I avoided that by using external
=curl=, =gzip=, and =gtar=.

This matters for repeatability.  A production project should not depend
on live Quicklisp downloading inside LispWorks 7.1 on this host.  It
should vendor sources, pin archives, or use an external fetch/extract
step.

** termbox, termbox2, notcurses, STFL, and libtcod Bindings

These are blocked by native dependency availability on this host.

- =cl-termbox= needs =libtermbox.so=.
- =cl-termbox2= targets =libtermbox2.so= and also hit a LispWorks
  compile-file problem.
- =cl-notcurses= needs =libnotcurses.so=.
- =cffi-stfl= needs =libstfl.so=.
- =tcod= / =cl-tcod= needs =libtcod.so=.

They should not be chosen unless we first decide to package those C
libraries for SmartOS native zones.

* Production Recipe

For a Croatoan or cl-charms project on =fido=, start from this runtime
shape:

#+begin_src sh
export PATH=/opt/tools/bin:/opt/tools/sbin:/usr/ccs/bin:/usr/bin:/bin:/usr/sbin:/sbin
export CPATH=/opt/tools/include/ncurses:/opt/tools/include
export LIBRARY_PATH=/opt/tools/lib
export PKG_CONFIG_PATH=/opt/tools/lib/pkgconfig
export LD_LIBRARY_PATH=/opt/custom/cl-tui/lib:/opt/tools/lib:/usr/lib/amd64:/usr/lib
export TERM=xterm
#+end_src

Then choose one of these deliberate ncursesw fixes:

1. Preferred: patch the library foreign-library definition to include
   =/opt/tools/lib/libncurses.so= or =libncurses.so= for SmartOS/pkgsrc.
2. Acceptable: install a controlled compatibility symlink:

#+begin_src sh
mkdir -p /opt/custom/cl-tui/lib
ln -s /opt/tools/lib/libncurses.so /opt/custom/cl-tui/lib/libncursesw.so
#+end_src

The second option is simple but should be documented, monitored, and
owned by the deployment.

* Recommended Next Test

Before writing a real application, build one small acceptance program in
Croatoan and one fallback program in cl-charms.  Each should:

1. Enter alternate/curses screen.
2. Draw a bordered main area and status line.
3. Display terminal size.
4. Read =q= to quit.
5. Read arrow keys.
6. Handle =Ctrl-C= or an error by restoring the terminal.
7. Exercise at least one color pair.
8. Run through =ssh -tt fido=.

If Croatoan passes that, use Croatoan.

If Croatoan fails on an application-specific input or layout path but
cl-charms works, use cl-charms and build the small layer needed.

If both are too high-level or too narrow, then compare =cl-fu= and
=raw-binding-ncurses=.

* Limitations

The tests here prove loadability and first terminal contact, not full
application maturity.

Not yet tested:

- Keyboard event mapping beyond minimal initialization.
- Arrow keys, function keys, escape timing, and mouse input.
- Resize events.
- Color-pair behavior beyond basic initialization.
- Unicode output and input.
- Long-running memory behavior.
- Delivered LispWorks images.
- Error recovery after asynchronous interruption.
- Multiple terminal emulators beyond =TERM=xterm= under SSH.

Those are the next gates before declaring a library production-ready for
a specific application.

* Final Answer

For LispWorks 7.1 on this SmartOS =fido= host, the practical dependency
choice is:

#+begin_example
Croatoan first.
cl-charms second.
cl-tui only if its older API is specifically desired.
cl-fu or raw-binding-ncurses only for raw ncurses work.
#+end_example

The adoption blocker is not Common Lisp.  It is the deployment boundary:
pkgsrc ncurses is wide-character capable but named =libncurses.so=, not
=libncursesw.so=, and CFFI grovel needs the =/opt/tools= include path.
Once those are made explicit, Croatoan, cl-charms, and cl-tui all work
well enough to proceed to an application-level prototype.

Do not choose the other surveyed libraries for this target today unless
the project explicitly includes patching LispWorks compatibility or
packaging additional native libraries for SmartOS.
