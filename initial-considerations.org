#+TITLE: cl-tui -- Initial Considerations
#+AUTHOR: SCS
#+DATE: 2026-07-03

* Purpose of this document

This project (=cl-tui=) collects core principles for building terminal
applications on *SmartOS* in *Common Lisp*, using a *commercial LispWorks*
license as the primary implementation. The goal is not a modern "TUI
framework" with panels, mouse support, and Unicode chrome. The goal is the
interaction model of older *MS-DOS*, *Xenix*, and *Unix shop* programs:
a clear screen, numbered choices, plain prompts, visible feedback while work
runs, and confirmation before destructive actions.

Think warehouse inventory, accounting entry, stock control, back-office
admin -- programs that lived entirely in the terminal and were operated by
staff who never saw source code and never typed arbitrary commands.

This document is a *considerations paper*, not a design spec or code. Where
a Lisp idiom or terminal mechanism is non-obvious, it is explained so later
code can share vocabulary. The intended reader includes newcomers who may
know little Common Lisp.

This document records language, platform, and design decisions for building
such applications on SmartOS. It is meant to guide *any* future operator
tool -- zone management, storage, networking, services, inventory, or
back-office workflows -- that shares this interaction style. Zone tooling
(=vmadm=, =imgadm=) is a motivating example, not the boundary of the
project.

* What we are building

** The warehouse-app interaction model

Characteristics we *want*:

- *Blank or cleared screen* at each major step (or a stable header + body).
- *Numbered menus*: "1. Create  2. Delete  3. List  0. Exit".
- *Single-key or short answers* where safe; typed strings where necessary.
- *Explicit feedback*: "Running job... please wait." during long operations.
- *Outcome lines*: "Done." / "Failed: reason." / "Record deleted."
- *Press Enter to continue* between screens when the operator must read a
  result before moving on.
- *Confirmation gates* before destructive work: "Delete item X? (Y/N)".
- *Disambiguation lists* when a short label matches several records
  (e.g. several images sharing a name, several datasets, several NIC tags):
  numbered list, pick one, no magic defaults.

Characteristics we *do not want*:

- Scrollable widget trees, split panes, modal dialog toolkits.
- Arrow-key-driven full-screen frameworks (ncurses "dashboard" style).
- Embedded web views, HTML, or browser-based UI.
- A free Lisp REPL exposed to the operator (no typing =(...)= at the prompt).
- Flashy progress bars unless plain text progress is insufficient.

** Visual vocabulary (fixed)

- Design to *80 columns by 24 rows*; degrade gracefully if smaller.
- *ASCII only*; reverse video at most (title bar, selected line).
- Stable screen regions on every screen:

#+begin_example
+------------------------------------------------------------------------------+  row 1-2  title
| MYAPP 1.0                            fido                        2026-07-03   |
+------------------------------------------------------------------------------+
|                                                                              |
|    1.  List items                                                            |  body:
|    2.  Create                                                                |  menu or
|    3.  Delete                                                                |  form
|    0.  Exit                                                                  |
|                                                                              |
+------------------------------------------------------------------------------+  row 24
| Enter choice: _                                        [ status message ]    |  prompt / status
+------------------------------------------------------------------------------+
#+end_example

** Name note

=cl-tui= is a working project name. "TUI" here means *terminal user
interface* in the historical sense (character terminal, line oriented),
not the modern ncurses/Bubble Tea/Textual meaning. If a better name appears
(=cl-shop=, =cl-console=, =cl-menus=), rename freely.

* Platform scope: SmartOS only

All design choices assume:

- The program runs in the *SmartOS global zone* (or a native SmartOS zone
  with the platform commands it needs), not Linux, not generic illumos, not
  macOS production deploy.
- The program orchestrates *SmartOS platform facilities* -- whatever commands
  and APIs the global zone provides for the task at hand (see below).
- Operator access is typically SSH into the global zone, often without a
  full login profile (non-interactive =PATH= is a recurring trap -- use
  explicit paths or a wrapper that sets environment).
- Third-party runtimes may exist under =/opt/tools/bin= on some hosts, but
  *this project does not depend on them*. LispWorks is the runtime we control.

Do not assume GNU/Linux man pages, =glibc= quirks, or Linux-only FFI when
reading external library documentation.

** Scope of SmartOS operations (open-ended)

=cl-tui= does not limit itself to virtualization commands. Any global-zone
operation that fits the warehouse-app model is in scope. Examples include
(but do not exhaust):

| Area            | Typical platform tools / concepts                    |
|-----------------+------------------------------------------------------|
| Zones / VMs     | =vmadm=, =imgadm=, =zlogin=, manifests, brands      |
| Storage / ZFS   | =zfs=, =zpool=, datasets, snapshots, quotas        |
| Networking      | =dladm=, =ipadm=, =flowadm=, NIC tags, static routes |
| Services        | =svcs=, SMF milestones, enable/disable, restarts   |
| System info     | =uname=, =prtconf=, =zonename=, platform buildstamp |
| Packages / images | =pkgin=, =imgadm avail/import= (where used)        |
| Jobs / audit    | long-running subprocesses, log tail, status files  |

Each *application* built on =cl-tui= chooses its domain. The shared library
holds interaction patterns (menus, prompts, disambiguation, subprocess
feedback); domain systems hold SmartOS-specific wrappers and data models
for that app's commands only.

Design for *extension*: new menu items and new command modules should not
require rethinking the operator model.

* Guiding principles

These win any conflict with cleverness below.

- *Clarity first.* The operator's screen and the maintainer's code should
  both be obvious.
- *Simplicity over machinery.* A numbered menu read line-by-line beats an
  event-driven widget tree. Reach for more only when the simple form
  genuinely cannot do the job, and say why.
- *One target, one terminal reality.* SmartOS only; ANSI/VT100-class terminal
  over SSH or serial. No abstractions whose only purpose is another platform.
- *Robustness above all* for an app that may *be* the operator's login. A
  single Lisp error must never drop a warehouse user into a debugger or a
  shell.

* Target environment details

** How the operator connects

- *SSH* (common case): pseudo-terminal, usually xterm-class. =TERM= is set.
- *Serial console* (lowest common denominator): plainer VT100; assume VT100
  if =TERM= is unset or unknown.

** Application as login program (warehouse pattern)

A dedicated role account can use the delivered binary as its *login program*
instead of a shell. The operator connects and lands directly in the menu; on
exit, the session ends. This is both good UX and a security boundary -- no
shell behind the app unless explicitly provided.

This interacts with account setup, SMF (usually not needed for per-login
interactive apps), and the build-time decision on the Lisp escape hatch
(see below).

** Deployment shape

- Deliver a self-contained binary; pin its version; install in the target
  zone (copy in or bake into zone image).
- SMF applies only if the program must run as a managed service, not for a
  typical per-login menu app.

* The terminal layer (concrete)

** Minimal primitive set

Resist a large terminal API. A menu-and-form app needs only:

- Clear the screen; move cursor to row/column.
- Write text at the cursor.
- Reverse video on/off (title bar, selected line).
- Ring the bell (invalid key).
- Read a line (cooked input) or, later, a single key (cbreak).

Everything the app draws is built from this contract.

** Implementation choices (settled recommendations)

| Decision | Recommendation | Rationale |
|----------+----------------+-----------|
| Escape sequences vs terminfo | Start with *direct ANSI/VT100* behind the abstraction | Safe over SSH on SmartOS; no curses dependency |
| Line input vs single-key | Start with *cooked* input (type + Enter) | Robust, scriptable, testable by piping text |
| Redraw strategy | *Full repaint* on state change | No incremental diffing; instant for menus |
| Encoding | *ASCII only* | Matches aesthetic; avoids width bugs |
| Exit paths | *Always restore terminal* (normal video, sane line discipline) | Every exit, including errors |

Revisit terminfo or cbreak per screen only when the simple form fails a
measured requirement.

** Signals and =TERM=

- Read =TERM= at startup.
- Decide treatment of interrupt (Ctrl-C), terminate, and window-change (may
  ignore resize and hold 80x24).
- Never leave the terminal in raw/no-echo mode after an error.

* Language and implementation

** Primary: Commercial LispWorks

- SCS holds commercial LispWorks licenses. This is the *authoritative*
  development and delivery target.
- Use LispWorks Delivery to produce a standalone executable (e.g.
  =smartos-ops= or =zone-tools=) whose entry is a custom =main=, not the IDE
  Listener.
- Delivery image is tuned for console use (=:interface :console= on Unix).
- Keep the delivered image focused: omit editor, compiler, and IDE pieces
  the operator does not need. Add only what the menu loop requires.
- *Disable the interactive debugger* in delivered images; route unexpected
  conditions to a log and a status-line message, never a debugger prompt.
- *Platform confirmed (2026-07-03, SmartOS host):* LispWorks 7.1.0
  =amd64-solaris= at =/opt/custom/lispworks= runs on SmartOS; =deliver= and
  =save-image= produce a standalone ELF binary with no separate runtime.
  Build and deliver *on the host* -- no cross-build shim required.

** Secondary: SBCL for smoke tests and fast loop

- SBCL builds and runs on SmartOS today -- use it for smoke tests and a
  fast development loop on the real host, not as a hedge against LispWorks.
- SBCL can produce an executable with a chosen top-level (analogous to
  Delivery) for testing the delivered-binary shape.
- Keep terminal control and image-building *behind the same abstraction*
  as LispWorks so screens and domain code do not know the implementation.
  Tests can supply a plain-text backend instead of a real terminal.

** Libraries and SCS.ASD policy

- Before adding dependencies, consult =~/infra/lisp/cl-lib/scs.asd=.
- Prefer accepted libraries already vetted for LispWorks and SmartOS native
  zones. Examine new libraries one at a time: FFI, native extensions,
  Quicklisp availability, build requirements on SmartOS.
- For warehouse-style apps, *prefer a tiny terminal abstraction* over
  ncurses or large FFI stacks unless a measured need arises later.

Live compatibility research on fido (LispWorks 7.1, pkgsrc ncurses, ASDF
load and SSH PTY smoke tests) lives in =lispworks-ncurses-survey-on-smartos.org=.
That survey is *orthogonal* to this design: it evaluates Croatoan, =cl-charms=,
and other ncurses frameworks if we ever need them. The default here remains
direct ANSI/VT100 primitives and cooked line input. *Name collision:* the
Quicklisp library =cl-tui= (naryl, ncurses widgets on =cl-charms=) is not
this repository's =cl-tui= shared operator layer.

* Operator interface vs developer interface

This distinction is central.

| Audience   | Interface              | Purpose                          |
|------------+------------------------+----------------------------------|
| Operator   | Delivered binary, menu | Day-to-day work on the shop floor |
| Developer  | LispWorks Listener     | Design, debug, extend, teach     |

** Operator: constrained command loop

The delivered binary runs something like:

#+begin_example
smartos-ops 1.0.0 -- SmartOS operator console

  1. Zones
  2. Storage
  3. Network
  0. Exit

Choice:
#+end_example

Submenus drill into domain actions (create zone, list pools, etc.). The
operator cannot evaluate arbitrary Lisp. They choose numbered options
and answer prompts. This is *REPL-like* only in the sense of repeated
read-eval-print *cycles you define* -- not a language REPL. Same shape as
=psql=, =gdb=, or a specialized debugger top-level.

** Build-time modes: operator vs administrator

Same codebase, different delivery profiles:

| Profile | Lisp escape hatch | Debugger | Typical deploy |
|---------+-------------------+----------+----------------|
| Warehouse operator | off | disabled | login program |
| Internal admin | optional | dev builds | SSH command |

** Developer: full Listener during development

In LispWorks IDE or batch development image:

- Load ASDF systems, inspect structs, call domain functions, test command
  parsers against live platform output on a SmartOS host.
- Use the Listener to refine prompts and data models before freezing them
  into the delivered menu loop.
- *Development liveness:* redefine a screen's draw or handler while the app
  runs, re-enter that screen to see the change -- a main reason to build in
  Lisp, at no cost at deploy time.

** Optional expert mode (later, maybe)

A hidden menu item or separate entry (e.g. =appname-dev=) could expose
more power. Default remains constrained. Do not ship the full Listener to
operators without an explicit decision.

* Core implementation principles

** Data model first

Before menus or Delivery scripts:

1. Identify entities for *this application* (zone, dataset, service, job
   result, manifest, etc.).
2. Represent them with plain =defstruct= (preferred over CLOS unless
   dispatch protocol is truly needed).
3. Define transformations (parse command output, resolve labels to IDs,
   build files or payloads for platform tools).
4. State invariants (required fields, mutual exclusions, confirm-before-delete).

Warehouse apps feel reliable when the *data* is explicit and the menus are
thin skins over validated operations.

** Application architecture

- *Domain vs presentation:* domain functions take and return data; no screen
  I/O in the domain layer.
- *Screens as functions; navigation as a stack:* each screen paints, reads
  input, returns a value; calling a sub-screen pushes logically, returning
  pops -- no separate state machine.
- *One input funnel:* all keystrokes through =read-line= / =read-key= so
  the app is scriptable and tests can feed text. The funnel needs *two modes*:
  block until a key (menus and forms), and wake on timeout as well as key
  (instrument panels while a job runs).
- *Redraw by repaint:* clear and repaint from current state; draw functions
  should be near-pure functions of state.
- *Conditions:* wrap each screen loop in a handler; in delivery, show a
  short status-line message and continue -- never crash out of the session.

** Screen and interaction conventions

Fix these once across all apps:

- *Menus:* numbered list, prompt =Enter choice: =; invalid input rings bell
  and shows one-line message, never unwinds the session.
- *Forms:* labelled fields one at a time, defaults in brackets (Enter
  accepts default), per-field validation, final review-and-confirm before
  commit.
- *Confirmation:* destructive actions require explicit yes, default no.
- *Keys:* consistent back, quit, accept keys; show them on the status line.
- *Process feedback:* state plainly before long work; for long jobs prefer an
  *instrument panel* (fixed frame, fields updated in place) over scrolling
  log lines; stream output or show a simple heartbeat; one clear result line
  at end. No fake spinners.

** Menus are thin; logic is testable

#+begin_src lisp
;; Menu layer (stdio)
(defun command-loop ()
  (loop ... (ecase (read-menu-choice) ...)))

;; Domain layer (testable without stdin)
(defun resolve-record (spec &key kind)
  ...)
#+end_src

SBCL smoke tests target the domain layer. LispWorks integration tests may
call real platform commands on a SmartOS host when available.

** Testing strategy

- *Domain, headless:* pure functions, no terminal (manifest build, parse
  =vmadm list=, validation).
- *Presentation, scripted input:* feed keystrokes through the input funnel;
  capture painted output via a dumb text backend (no escape sequences in
  assertions).
- *Golden screens:* for stable menus, compare expected text snapshots; assert
  invariants (items listed, bad input rejected) rather than exact escape bytes.

** Feedback during long work

SmartOS operations (zone create, =zfs send=, service restart, large
imports) may take seconds to minutes. The operator must never stare at a
frozen screen.

#+begin_example
Running operation 'create-zone'...
(This may take a while.)
#+end_example

Print status *before* calling external commands. Stream subprocess output
when helpful (=uiop:run-program= with appropriate stream arguments). Print
a clear completion line with UUID or error.

** Disambiguation instead of guessing

When a label matches multiple records (common with catalog listings,
installed images, dataset names, or service instances), *never* pick the
first match silently.

#+begin_example
Multiple images match 'ubuntu-24.04' for brand lx:

  1. ubuntu-24.04  20250407  lx-dataset  8a1b6e3a-...
  2. ubuntu-24.04  20250627  zvol        97219479-...

Enter number:
#+end_example

The underlying API often requires an opaque ID (UUID, FMRI, dataset path);
the menu layer resolves human-friendly specs and numbered picks.

** Confirm destructive actions

Delete, overwrite, reprovision -- always confirm unless =--force= on a
scripting path (batch flags are a separate, explicit mode).

** Screen discipline

- Clear or redraw consistently (=cli:clear-screen= or fixed layout).
- One concept per screen when possible.
- Avoid scrolling walls of text; paginate long lists ("Press Enter for
  next page") in the old style if needed.

** ASCII only in operator-facing text

Use =--= not em-dash, plain quotes, no fancy ellipsis. Terminals on shop
floors and serial consoles reward boring text.

* External command integration (SmartOS)

Warehouse apps orchestrate platform tools rather than reimplement them.

- Wrap each SmartOS command (or stable shell pipeline) in a small module
  with explicit argument lists and parsed result types.
- Parse tabular or line-oriented output defensively; platform output formats
  vary by command and version.
- Surface subprocess failures as operator-readable messages, not Lisp
  condition backtraces (log traces to a file or stderr in debug builds).
- Use absolute paths (e.g. =/usr/sbin/vmadm=, =/sbin/zfs=) when =PATH=
  may be minimal.
- Centralize "run command with feedback" in =cl-tui= so every application
  behaves consistently during long jobs.
- *Transparency (SMIT ethic):* before running a platform command, show the
  operator the exact invocation; run it; stream output; log it for replay.
  A menu wrapper that hides the command becomes a black box; one that shows
  it earns trust and teaches capable operators.

Some operations may later use ioctl, libzfs, or other FFI -- treat each as
a separate adoption decision under SCS.ASD policy. Default remains
subprocess orchestration of existing CLI tools the operator already trusts.

* Delivery and distribution

We are *not* optimizing for a single static binary in the Go sense, but
LispWorks Delivery *does* produce one executable the operator can run.

Typical flow:

1. Develop in LispWorks on SmartOS (or cross-develop with care).
2. Load ASDF system and Delivery script.
3. =deliver= produces the application binary (name per app).
4. Install under =/opt/.../bin= on SmartOS hosts.
5. Upgrade by replacing the delivered binary and release notes.

Document required LispWorks runtime assumptions (console, 64-bit, etc.).
Version the operator-facing banner (=myapp 1.2.0=).

SBCL has no parallel Delivery story; do not rely on SBCL for operator deploy.

* Why Common Lisp fits this style (honest lean)

Other languages were considered for SmartOS operator tooling (shell, Go,
Python, Node). For *this* interaction model on SmartOS:

- *Warehouse menus* are easy with =read-line=, =format=, and structured
  loops -- no framework required.
- *LispWorks Delivery* gives a single operator command without Python venvs
  or Node module trees.
- *Development joy* lives in the Listener: inspect records, retry parsers,
  teach juniors with live data from the machine.
- *Data-driven design* matches s-expression configs and =defstruct= models
  before wire-format ceremony at API boundaries.

Go and Python excel when the product is "polished terminal dashboard" or
"pip install everywhere." Common Lisp excels when the product is
*controlled shop-floor interaction* plus *deep leverage for the author*.

The hinge is not "which widget toolkit" but *whether the operator may speak
the language*. Warehouse apps say no; developers say yes in the IDE.

* Anti-patterns to avoid

- Shipping the full Listener as the production UI.
- Silent defaults when a list command returns multiple matches.
- Fancy ncurses layers before plain menus prove insufficient.
- Assuming =#!/usr/bin/env= or =PATH= on non-login SSH sessions.
- CLOS-heavy designs when =defstruct= and functions suffice.
- Linux-only library docs applied blindly to SmartOS.
- Hiding long platform work with no progress message (operators think it hung).
- Baking one app's domain into the shared =cl-tui= library.
- Incremental screen diffing instead of full repaint (complexity without benefit).
- Leaving terminal in raw/no-echo mode after an error.
- Invalid menu input that unwinds the session or prints a Lisp traceback.

* First proving-ground application (example)

A zone tool is a natural first program -- not the only one =cl-tui= will
serve, but it exercises every convention:

- Main menu: list, create, delete, quit.
- Create: form (brand, *select image from numbered list*, RAM, disk, network),
  review-and-confirm, provision with visible feedback, result line.
- Delete: show target, explicit yes, stop if running, confirm.

** Illustrative example: ambiguous image names (zones)

- =imgadm avail name=base-64-lts= shows many versions (14.4.0 ... 25.4.0).
- =imgadm list= on a host shows only installed images, but =ubuntu-24.04=
  may appear twice (=lx-dataset= vs =zvol=).
- Operator enters =base-64-lts:24.4.1= or picks from a numbered list.
- The payload sent to =vmadm= uses a UUID; the menu layer resolves the label.

A storage app might disambiguate =tank/data= vs =tank/data@snap= the same way.

* Prior art: golden examples to study

The style we want is not new; it was ordinary serious software for two
decades. Rather than invent conventions, steal them from programs that
already solved this. What follows is curated, grouped by what each teaches
best. Zone tooling is used in examples; the same patterns apply to storage,
networking, services, and back-office apps.

** Three screen archetypes

Name these explicitly -- a common mistake is building one archetype with
the reflexes of another:

- *MENU* -- numbered choices; program mostly idle, repaints on operator action.
  Event-driven.
- *FORM* -- labelled fields, per-field validation, final confirm. Cursor moves
  field to field. Event-driven.
- *INSTRUMENT PANEL* -- fixed frame whose fields update in place while a long
  task runs (percentage, counter, elapsed time). Time-driven: repaints on a
  clock, not only on keypress; never idle while the job runs.

memtest86 is the canonical instrument panel. Most classics below are menu or
form. We need all three.

** Menu and administration driver

*** AIX SMIT -- primary golden example

SMIT (System Management Interface Tool) is the closest ancestor of a SmartOS
operator tool. Menus drill to a task; the task presents a form; then -- its
signature move -- SMIT shows the *exact command line* it is about to run,
runs it, streams output with plain running / OK / failed status, and logs
the command for replay. That "show the command, then run it" habit is the
most valuable single idea in this list.

*** SCO sysadmsh -- cultural ancestor

sysadmsh (System Administration Shell on SCO Xenix/UNIX): full-screen menu,
first-letter navigation, command-and-status line pinned at the bottom like
an editor minibuffer. If SMIT teaches task flow, sysadmsh teaches the overall
frame.

*** HP-UX SAM -- the sibling

SAM (System Administration Manager) -- same era, same idea as SMIT: menus
into forms into actions. A second data point on how the giants structured this.

** Data-entry form -- warehouse and back-office archetype

*** Informix PERFORM -- definitive character-mode business form

PERFORM shows labelled fields over a database row, with a *ring menu* across
the top -- single-key verbs (Query, Next, Add, Update, Remove, Browse) -- and
a status line beneath. Nearly every Xenix/UNIX warehouse and accounting app
felt like this. Steal the ring menu and fixed status line wholesale.

*** Progress 4GL character mode ("chui")

Same lesson as PERFORM; what enormous numbers of manufacturing and warehouse
systems actually ran for decades.

*** DOS accounting packages

DacEasy, Peachtree Complete for DOS, dBASE III/IV ASSIST -- literal shop and
back-office systems: menu tree, data-entry form behind each function, printed
reports. The exact flavour we are evoking.

** Instrument panel -- process feedback

*** memtest86 / memtest86+

Fixed frame rewritten in place while a long job runs -- pass count, errors,
test percentage, elapsed time. Exactly how a "provisioning zone (this can
take up to a minute)" screen should behave: paint a frame once, update numbers
inside it; do not scroll log lines at the operator.

*** top / htop

Same "keep the frame, rewrite fields on a timer" technique in tools you can
run today. Clearest live demo of time-driven repaint.

** Command legend and overall feel

*** PINE -- persistent command legend

Two-row command legend pinned at the bottom: the keys that act *right now* are
always visible. Adopt for our status/prompt line on every screen.

*** Still-runnable minimal menus

For living reference: =nmtui=, =raspi-config=, FreeBSD =bsdconfig= -- descend
from dialog/libdialog (boxed menus, checklists, progress gauges). If we ever
want boxes, this is the restrained end to copy.

** Admire, but do not over-copy

Study for ideas, not as templates:

- *Norton Commander / Midnight Commander* -- two-pane file manager, function-key
  bar. More apparatus than we want; PINE gives the legend idea more simply.
- *Borland Turbo Vision* -- pull-down menus, movable dialogs, drop shadows.
  Precisely the "modern framework" aesthetic our non-goals rule out.
- *Lotus 1-2-3* -- slash-key command bar with one-line description. Elegant,
  richer than a numbered menu needs.
- *WordPerfect 5.1* -- near-blank screen, single modest status line: purest
  "blank screen, nothing you do not need" ethos.

** If you study three

Study *SMIT*, *Informix PERFORM*, and *memtest86*. They map one-to-one onto
menu driver, data-entry form, and process panel -- and cover the whole
application between them.

interaction and subprocess conventions. Each SmartOS app adds its own
=platform/= tree as its scope grows.

* Open questions (to resolve before large implementations)

1. LispWorks on SmartOS -- *resolved* (2026-07-03): 7.1.0 amd64-solaris at
   =/opt/custom/lispworks=; delivery verified on host.
2. Line input vs single-key for first screens (recommendation: cooked first).
3. Direct ANSI vs terminfo (recommendation: ANSI behind abstraction first).
4. How the app is installed as a login program; lockdown level per role.
5. Confirm =TERM= values on SSH vs serial console on production hosts.
6. Where delivered binaries live (=/opt/tools/bin=? per-app =/opt/APP/bin=?).
7. Logging: file per run, syslog, or stderr-only in debug deliveries.
8. Wire formats at API boundaries vs internal s-expression models.
9. Whether =--force= batch flags exist alongside the menu binary for scripts.
10. How multiple apps share one =cl-tui= library version on the same host.
